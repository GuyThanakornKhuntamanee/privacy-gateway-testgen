# Security Policy

## Scope

`privacy-gateway-testgen` generates **synthetic** privacy, payment, credential
and infrastructure test data. It is a test-data generator, not a privacy
gateway, DLP engine, or compliance certification tool.

## Safety properties

- No network requests, telemetry, analytics, or third-party dependencies.
- No real customer, patient, employee, or payment data is bundled.
- Emails use reserved domains: `example.com`, `example.org`, `example.net`,
  and `.invalid`.
- Internal names use reserved `.internal` / `.example` names.
- IPv4 values use RFC 1918 private space or RFC 5737 documentation ranges;
  IPv6 uses `fd00::/8` (ULA).
- Cards use documented test BINs (Visa `411111`/`424242`, Mastercard `555555`,
  Discover `601111`, Amex `378282`) and are Luhn-valid. CVVs and expiries are
  synthetic.
- AWS-like access keys contain `FAKE`/`EXAMPLE`.
- PEM blocks use labels such as `EXAMPLE FAKE PRIVATE KEY`, which real TLS/SSH
  parsers reject.
- JWTs have a fixed fake payload and the literal signature
  `example-fake-signature`.
- Cloud resource IDs use account `000000000000` and example resource names.
- `tests/test_security.py` scans a generated dataset for live-credential
  markers and validates these properties.

These controls make values safe to publish. They do **not** prove that a third
party will never misclassify a test value, and they do **not** constitute PCI
DSS, HIPAA, GDPR, PDPA, or any other compliance certification.

## v2 file generation

The schema 2.1 generator writes real files. It enforces additional controls:

- OOXML packages are created directly with `zipfile` and XML; they contain no
  macros (`vbaProject.bin`), executables, DLLs or remote templates.
- DOCX/XLSX/PPTX ZIP entries use fixed timestamps and contain no external
  relationships other than safe `example.org`/`example.com` documentation links.
- PDFs contain no JavaScript, `/OpenAction`, `/Launch`, embedded files or remote
  content. They may embed a locally generated RGB image for scanned-page tests.
- Spreadsheets contain values, not formulas; no external workbook links or
  WebDAV paths are emitted.
- Images are synthetic screenshots/scans drawn by the renderer. They are marked
  `SYNTHETIC SAMPLE` where appropriate, contain no real identity documents and
  do not depict real people.
- All generated credential strings remain non-functional and carry
  `example`/`fake`/placeholder markers. The v2 security test scans every
  generated byte for live-credential markers.
- `tests/test_v2_security.py` scans Office packages, PDFs, images and entity
  values in a generated sample.

Image OCR annotations are **pre-render ground truth**. The test suite does not
run an OCR engine; image and scanned-PDF cases are marked `verified_layout` and
must not be presented as OCR accuracy evidence.

PDF and image renderers are Latin-only. A Thai request for those renderers is
routed to English and recorded as `language_routing`; the renderers raise on
non-Latin text instead of writing `?`. Thai content belongs in DOCX, XLSX, PPTX
or text formats. No Thai PDF or Thai OCR-image capability is claimed.

Cross-file links and arithmetic checks describe the generated scenario only.
They do not certify that a downstream gateway performs the same correlation.

## Collision risk of synthetic identifiers

Some entity factories deliberately produce shape-valid values so detectors face
realistic input. They are synthetic, but they are not guaranteed collision-free:

- **Thai phone numbers** follow a real mobile shape (`06`, `08` or `09`
  prefix). The value space is shared with assigned numbers, so a random value
  can resemble a real subscriber number. No reserved Thai mobile range exists
  that would keep the format useful for detection tests.
- **Thai national-ID-shaped values** are 13 digits with a valid modulus-11 check
  digit. A random number can therefore be checksum-valid; the probability of
  matching any real citizen ID is small per value but not zero across a large
  dataset.
- **Bank account numbers** follow a common Thai display shape but do not encode
  a real bank/branch/account scheme and are not verified against any bank.
- **Thai addresses** use public province/district/subdistrict names from a
  curated table, but the house number, moo and soi are random and no street
  number is derived from real household data.

Mitigations: values are only generated inside synthetic scenarios, every value
is annotated as synthetic, and the collision risk is documented here rather than
silently assumed away. Do not publish a dataset as "safe PII" on the basis of
this generator; treat it as a test fixture. If an exact match with a real person
or account is ever discovered, report it as a security issue and remove that
value from the released dataset.

The alternative (invalid prefixes or obviously fake values) was rejected because
it would make the detector benchmark trivial. The tradeoff is deliberate:
synthetic realism for detector testing, with documented residual risk.



Generated datasets are synthetic but may still be flagged by DLP scanners,
secret scanners, or antivirus heuristics. Handle them like test fixtures:

1. Label the dataset as synthetic in filenames and repository metadata.
2. Keep real policy files and real detector configurations out of public
   artifacts when they are confidential.
3. Do not merge generated datasets with real customer data.
4. Review the `manifest.json` config/policy hashes before publishing a dataset
   so the provenance is clear.

## Reporting a vulnerability

If you find a real credential, personal record, production endpoint, or
proprietary company detail in the repository or generated output, do not open a
public issue with the value. Report it privately to the maintainers of the
repository where you obtained this project, including:

- the file and line,
- the entity type and why it appears real,
- the generator seed and template if applicable.

Remove or rotate any exposed secret immediately; assume any credential that
looks real may be real.

## Misuse considerations

The tool intentionally produces realistic-looking fake identifiers to test
detection systems. Do not use it to impersonate people, bypass authentication,
or fabricate evidence. The values are non-functional by construction; if a
generated value ever works against a real system, treat that as a severe bug
and report it.

## Dependency and supply-chain posture

- Runtime dependencies: none (Python standard library only).
- Tests: Python standard library `unittest`.
- No package installs are performed by the generator.
- The CI workflow uses GitHub-hosted runners and `actions/setup-python`; pinning
  action SHAs is recommended for hardened deployments.

## Supported versions

Security fixes are applied to the latest `0.x` release until a stable `1.0`
line exists.
